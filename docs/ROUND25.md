## 方法

保留常驻 CPU owner 与完整专家计算；把逐层的请求/等待 kernel 替换为 CUDA Driver 的 BatchMemOp 流内存操作：

- `complete=0` 发起请求；
- `request=1` 写入完成；
- `wait complete=1` 在流上等待；
- 捕获时显式加入 BatchMemOp 图节点并更新依赖；eager 路径使用 `cuStreamBatchMemOp`。

主机线程不再为空转等待的 kernel 让出 SM，GPU 按流依赖自行等待。源码与构建脚本见
[`patches/round25-batchmemop`](../patches/round25-batchmemop/)。

## 完整服务 A/B/A

每阶段先做六项功能检查与单流/八路热身，再执行两次正式测试：单流 3000 token、八路总 8192 token。

| 阶段 | 单流 decode token/s | 单流端到端 token/s | 八路端到端聚合 token/s |
|---|---:|---:|---:|
| 原版 A1 | 52.73 / 52.16 | 51.03 / 50.45 | 118.63 / 119.63 |
| 候选 B | 55.35 / 55.58 | 53.36 / 53.60 | 112.69 / 109.00 |
| 原版 A2 | 51.23 / 50.80 | 49.53 / 49.22 | 107.54 / 108.57 |
| 候选 B2 | 54.30 / 55.26 | 52.45 / 53.29 | 116.43 / 118.84 |
| 原版 A3 | 52.03 / 52.12 | 50.41 / 50.53 | 110.73 / 113.15 |

- 原版 6 次单流均值 **51.85**，候选 4 次均值 **55.13**，描述性差异 **+6.3%**。
- 八路聚合原版 **107.54–119.63**、候选 **109.00–118.84**，没有一致提升。
- 自由生成内容、草稿接受率与缓存学习轨迹存在差异；不能把均值差直接归因为单一调度改动。

## 上线复测与验收

候选已切换为生产版本；切换时清空专家缓存学习状态。上线后四轮单流复测：

| 轮次 | 单流 decode token/s | 端到端 token/s | 八路聚合 token/s |
|---|---:|---:|---:|
| 1 | 52.86 | 51.06 | 111.03 |
| 2 | 54.10 | 52.27 | 113.42 |
| 3 | 54.48 | 52.45 | 117.56 |
| 4 | 55.72 | 53.70 | 115.51 |

均值 **54.29**。分数随专家缓存学习逐步上升；前两轮偏低。

验收结果：

- 六项功能检查 6/6 通过（JSON 算术 ×3、多轮、工具调用、长输入）；
- `/health`、`/v1/models` 返回 200；`/collective_rpc`、`/start_profile` 返回 404；
- 请求与排队均为 0；切换后日志 0 ERROR；
- 原库与原专家状态已备份，可按部署文档回滚。

回滚流程：停止生产服务 → 恢复备份的原库与专家状态 → 重启服务 → 执行六项功能检查。具体命令见
[`DEPLOYMENT.md`](DEPLOYMENT.md)，本仓库不发布内部服务名与绝对路径。

## 边界与下一步

- 单流 **65/80 token/s 未达到**；从 55.13 到 65 仍需约 17.9%，到 80 需约 45.1%。
- 八路没有一致提升；当前优化主要收益在单流。
- 下一步是多 rank CPU 专家与缓存所有权重构，而不是继续微调单个 kernel。
- 以上为短时、固定输出预算的描述性结果，不构成对其他硬件或负载的性能承诺。
